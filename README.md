**Live demo:** [procure-sense.streamlit.app](https://procure-sense.streamlit.app)

- **Phase 1 — Schema Design:** Designed and deployed the full Postgres schema (10 tenant-scoped tables: tenants, suppliers, contracts, contract_items, contract_chunks, purchase_orders, invoices, reconciliation_results, audit_log, agent_runs, llm_cache) with Row-Level Security enforced at the database layer. All natural-key uniqueness constraints are tenant-scoped. Diagnosed and fixed a false-pass in initial testing caused by Supabase's default `postgres` connection being a superuser that bypasses RLS; created a dedicated `app_user` role (`nobypassrls`) matching real application permissions. Verified genuine tenant isolation with a two-tenant insert/read test under those permissions.

- **Phase 2 — Synthetic Data Generation:** Generated a reproducible (seeded), tenant-scoped synthetic dataset: 2 tenants, 8 suppliers each, ~10 contracts with structured contract_items, ~40 purchase orders and invoices per tenant. Invoices are labeled across 5 categories with a known ground truth (data/synthetic/ground_truth.json): clean/approved (60%), price-variance leakage (20%), duplicate PO (10%), missing-contract (5%), and ambiguous edge cases (5%, held out — not used to tune detection logic, reserved for Phase 11 eval only). Also generated 3 real contract PDFs with actual clause text for later RAG/citation testing.

- **Phase 3 — Deterministic Reconciliation Engine:** Built a pure SQL/Python reconciliation engine (no LLM) checking every invoice against three rules: PRICE_VARIANCE (>5% over contracted price), MISSING_CONTRACT (no active contract_item match), DUPLICATE_PO (shared PO across invoices). Initial validation showed 71% recall — traced to a state-reset bug in the Phase 2 data generator where "duplicate" POs were never actually reused, so no true duplicates existed to detect. Fixed the generator, regenerated data, and revalidated: 100% precision, 100% recall, 100% check-type accuracy across 28 labeled leakage cases and 48 clean invoices, zero false positives. Held-out ambiguous edge cases (0.5–2% variance) are correctly treated as within-tolerance at the current 5% threshold — informational data point for future threshold tuning, not a defect.

- **Phase 4 — Validated Extraction Pipeline:** Built a PDF-to-structured-data pipeline (PyMuPDF → Groq LLM → Pydantic validation) for contracts and invoices, with retry-on-validation-failure (up to 3 attempts, validation error fed back into the retry prompt) and tenant_id injected post-extraction rather than trusted from LLM output. All 3 contracts and 3 invoices (including a deliberately messy, inconsistently formatted one) extracted successfully with zero retries needed. Found a real limitation: an ambiguous date format (03-08-2026) was parsed as a plausible but unverifiable interpretation — Pydantic validates structure, not semantic correctness, which is exactly the gap the Phase 8 human-in-the-loop review is designed to catch. Every extraction attempt logs tokens, latency, and status to agent_runs. Hit and resolved a groq/httpx version incompatibility (`proxies` kwarg removed) by upgrading groq to 1.6.0; locked the full environment with `pip freeze` for reproducibility.

- **Phase 5 — Cited Contract RAG:** Chunked contract PDFs page-by-page (PyMuPDF), embedded via Google gemini-embedding-001 (768-dim, output_dimensionality pinned to match schema — text-embedding-004 was deprecated mid-build), stored in contract_chunks with pgvector. Hybrid search blends pgvector cosine similarity and Postgres native ts_rank full-text in one weighted SQL query (0.7/0.3), using CAST(:emb AS vector) rather than the :param::vector shorthand, which SQLAlchemy's bound-parameter parser mishandles. A Pydantic-validated LLM rerank layer narrows results to a cited top-3 with page numbers and relevance rationale. Verified against 3 test questions — each correctly surfaced the right contract/page first, with honest relevance reasoning even for tangential runner-up candidates. Known scale limitation: current corpus is only 3 chunks total (one per short synthetic contract), so retrieval selection isn't meaningfully stress-tested yet — ranking quality is confirmed, selection-at-scale is not.

- **Phase 6 — LLM Router + Semantic Cache:** Built call_llm() wrapping Groq (primary) with automatic Gemini fallback, two-tier cache (exact SHA-256 hash, then semantic cosine similarity) checked before any API call, real per-model cost estimates logged to agent_runs for every call. Initial semantic threshold (0.95, an unvalidated default) never fired — measured actual similarity on gemini-embedding-001 for a true paraphrase (0.792) vs. a genuinely different question (0.658), and recalibrated to 0.75 based on that empirical gap. Noted as a starting calibration from 2 data points, not a rigorous study — a production system would want a labeled set of dozens of paraphrase/non-paraphrase pairs before trusting this threshold at scale.

- **Phase 7 — LangGraph Multi-Agent Orchestration:** Built a supervisor + 3 sub-agent system (Supplier Intelligence, Anomaly/Leakage, Negotiation Drafting) using LangChain's `create_agent`, routed by an LLM-based supervisor constrained to 4 exact labels. All agents share tools wrapping the existing Phase 3 reconciliation engine, Phase 5 hybrid search/rerank, and Phase 6 LLM router — no logic duplicated. Cross-turn memory via LangGraph's Postgres-backed checkpointer (`langgraph-checkpoint-postgres`), keyed by `thread_id`, using a dedicated `psycopg` v3 connection pool separate from SQLAlchemy's `psycopg2` driver.

  Hit and resolved 7 distinct issues in getting this working, several revealing real architectural decisions rather than simple bugs:
  1. `PostgresSaver.from_conn_string()` returns a context manager, not a usable checkpointer directly.
  2. Checkpoint table creation requires `CREATE` privilege that `app_user` deliberately lacks (Phase 1 least-privilege design) — moved table setup into a one-time admin-only migration script, with `app_user` granted read/write (not create) afterward.
  3. The context-manager pattern didn't keep the connection alive reliably across function scopes — replaced with a module-level `ConnectionPool` (`autocommit=True, prepare_threshold=0`), the documented pattern for a long-lived checkpointer.
  4. The router crashed with `KeyError` if the supervisor node failed internally before setting its output — made the router fail closed to `"end"` on any error (malformed LLM output, API failure) instead of ever crashing the graph; a routing layer should degrade gracefully, not take down the request.
  5. `create_agent()`'s `prompt` argument was renamed to `system_prompt` in the currently installed LangChain version — verified directly against installed source rather than guessing.
  6. The `"groq:model-name"` shorthand routes through LangChain's `init_chat_model`, which needs the separate `langchain-groq` package.
  7. Groq's tool-call schema validation occasionally rejected a numeric argument (`limit`) that the model emitted as a string — a known tool-calling quirk on `llama-3.3-70b-versatile`, not a code bug. Fixed by declaring the parameter as a string with internal `int()` coercion, the standard defensive pattern for this class of model non-determinism.

  Final 3-turn same-thread test passed clean: Turn 1 (anomaly question) correctly routed and returned 14 real flagged invoices with accurate check_type/severity, no hallucinated numbers. Turn 2 (supplier intel question) correctly routed, cited **CON-002, Page 1, INR 35.50** — matching the independent Phase 5 RAG result exactly, confirming genuine tool use rather than guessing. Turn 3 (negotiation request) correctly routed and drafted an email that explicitly stated it requires human approval before sending, confirming the no-send-capability framing that Phase 8's human-in-the-loop gate will build on.

- **Phase 8 — Human-in-the-Loop + Audit Trail:** Added a real approval gate on the Negotiation agent's drafts using LangGraph's native interrupt()/Command(resume=...) pattern — the graph genuinely pauses (persisted by the Postgres checkpointer), not just a prompt instruction. Discovered and fixed two real issues: (1) the sub-agents' create_agent() calls used a raw "groq:model-name" shorthand with no fallback, so Groq's daily token quota exhaustion crashed them outright — fixed with a shared ChatGroq.with_fallbacks([ChatGoogleGenerativeAI]) model used by all three agents, plus durable agent_runs logging on the supervisor's fail-closed path; (2) interrupt() replays the entire node function from the top on every resume, which caused entity_id generation and the DRAFTED audit log write to fire twice per draft — fixed by moving that one-time logic into negotiation_node, which completes before human_approval_node runs and is never replayed. Verified all three decision paths (approve as-is, approve-with-edits, reject) end-to-end with exactly one DRAFTED + one decision row per scenario in audit_log, correct diffs, and distinct content hashes for edited vs. unedited drafts.

- **Phase 9 — SQL Agent + Read-Only DB Role:** Built a natural-language-to-SQL agent with two independent security layers: a dedicated sql_agent_ro Postgres role with SELECT-only grants (DB-level, inherits RLS automatically), and app-level guardrails (single-statement check, forbidden-keyword blocklist, forced LIMIT) rejecting unsafe SQL before execution. Discovered a real Phase 6 semantic-cache blind spot: prompts sharing a large fixed schema-context block with only a short variable question produced near-identical embeddings regardless of the actual question, causing incorrect cache hits across genuinely different queries — fixed by disabling caching for this call site. Verified 3 legitimate analytical questions produce correct, distinct SQL and results; a direct DELETE attempt was correctly blocked by the app-level guardrail. Verified the multi-statement/DROP guardrail directly against known-malicious SQL strings (bypassing the LLM, since a well-behaved model declining to generate an injection isn't proof the guardrail itself works) — all adversarial patterns correctly blocked.

- **Phase 10 — Security Guardrail Middleware:** Added two deterministic (regex-based, not LLM-based) guardrails so neither can itself be talked out of its job by adversarial input. PII redaction (email, Indian phone numbers, PAN, IFSC codes, credit card numbers) runs on every negotiation draft before a human reviews/approves it — catching accidental leakage of internal personal data into supplier-facing text. Prompt-injection detection scans ingested contract/invoice text before it reaches any LLM in the extraction pipeline (Phase 4); a flagged document is blocked from extraction entirely and logged with status=BLOCKED_INJECTION, rather than silently "cleaned" and processed. Following the Phase 9 lesson, guardrails were tested directly against known-adversarial input, not only through the LLM, since a well-behaved model declining to misbehave isn't proof the guardrail code itself works.

- **Phase 11 — Eval Harness:** Consolidated evaluation: reconciliation 100%/100%/100% (Phase 3, reused), extraction accuracy 100% across all 3 contracts and 2 test invoices, citation correctness 100% (RAG cites the exact right contract/page for all 3 known-answer questions), LLM-as-judge scoring negotiation drafts 5/5 on tone and factual grounding. Found and fixed a real scope gap: the eval initially scored `clearly_states_approval_needed=False` because it calls `draft_negotiation_email` directly, bypassing the LangGraph negotiation_node whose system_prompt (not the tool itself) carried that instruction. Fixed by moving the approval-required framing into the tool's own prompt, so it holds whether the tool is called standalone or via the full agent graph.

- **Phase 12 — MCP Wrapper + Lightweight Telemetry:** Exposed core tools (get_flagged_invoices, search_contract_clauses, run_reconciliation, ask_procurement_data) as a real MCP server (stdio transport) wrapping existing Phase 3/5/9 logic — no reimplementation. Verified all 4 tools directly: correct flagged invoices, correct cited contract clauses matching Phase 5's proven output exactly, correct SQL-agent results. Added a SQL-based telemetry summary over agent_runs (captured since Phase 4) instead of a full distributed tracing stack — aggregates call count, success/error counts, avg latency, and total cost per agent. Fixed two real bugs surfaced while building this: telemetry query missing set_config('app.tenant_id', ...) returned zero rows under RLS (same class of bug as Phase 1's original RLS test), and NULL avg/sum on all-NULL-latency rows crashed Python's format string — fixed with COALESCE in SQL. Final telemetry report honestly reflects the project's actual debugging history, including a real embedder error rate from earlier Phase 5 API issues, now permanently visible as evidence rather than hidden.

- **Phase 13 — Streamlit Dashboard:** Built a 5-tab dashboard tying together every phase: flagged invoices + one-click reconciliation re-run + invoice upload/extraction, cited contract search (Phase 5 RAG), negotiation drafting with an in-UI human-in-the-loop approval flow (approve/edit/reject, all logged to audit_log via Phase 8's log_decision), the SQL agent (Phase 9), and live per-agent telemetry (Phase 12). The UI's approval flow calls the negotiation logic directly with st.session_state managing the pause-for-review step, rather than round-tripping through LangGraph's interrupt()/checkpointer — a deliberate choice, since interrupt() is designed for programmatic pause/resume across process boundaries (proven in Phase 8's test), while a UI naturally has its own pause point at the button click.

- **Phase 14 — Deployment:** Deployed the Streamlit dashboard to Streamlit Community Cloud (Supabase DB required no migration — the payoff of choosing a managed cloud Postgres from Phase 0). Removed the unused, empty `app/api/` scaffold rather than leave a half-built FastAPI layer — nothing in the project (dashboard, agents, MCP server) depends on it; the MCP server uses stdio transport and runs locally against a host config, which is standard MCP practice, not a gap. Hit and resolved two real deployment issues: (1) `requirements.txt` from a Windows `pip freeze` included `pywin32`, which fails to resolve on Linux containers — trimmed to direct dependencies only; (2) Streamlit Cloud defaulted to Python 3.14, which has no prebuilt wheel for `psycopg2-binary`, causing a `pg_config not found` build failure — `runtime.txt` is currently a known, open Streamlit Cloud bug and gets silently ignored, so the working fix is pinning the Python version explicitly via the deploy-time "Advanced settings" dialog instead. Also fixed a styling bug where CSS alone couldn't override Streamlit's native dark-theme text color, causing white-on-white invisible text — corrected with a proper `.streamlit/config.toml` light theme, with custom CSS layered on top only for accents.
